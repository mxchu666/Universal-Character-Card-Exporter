# Universal Character Card Exporter

[English](README.md) · [Español](README.es.md) · [日本語](README.ja.md) · [Italiano](README.it.md) · [Deutsch](README.de.md) · **Русский**

Расширение для браузера, которое читает персонажа с **JanitorAI**, **Emochi**, **Polybuzz**, **Character.ai**, **Crushon.ai**, **Saucepan.ai**, **Chub.ai**, **Venus.chub.ai** или **WyvernChat** и сохраняет его как переносимую карточку персонажа — для резервной копии или переноса на другой фронтенд. Без аккаунта, без сборки, без сервера. Работает в вашем браузере, под вашей сессией.

**Новое в 0.12.0:** читатели Chub.ai, Venus.chub.ai и WyvernChat, определение JanitorAI, восстановленное из собственного дважды закодированного хранилища гидратации страницы, **Save chat** для Character.ai (Tavern JSONL, JSON, Markdown, пример диалога и файл пар для Oobabooga) и все поля карточки V2/V3, включая параметры записей `character_book`. Путь PNG был перестроен и прочитан обратно в настоящем браузере: `chara` + `ccv3`, оба перед `IDAT`, портрет цел. Подробности в [changelog](CHANGELOG.md) и в [devlog](#devlog).

> Бесплатно и с открытым кодом. Если пригодилось и хочется поддержать исходную работу — загляните на [inkwell.rip](https://inkwell.rip). Именно это позволяет таким инструментам существовать.

## Что экспортируется

| Формат | Файл | Кто читает |
|---|---|---|
| Карточка SillyTavern | `.card.json` | SillyTavern, Tavo, Agnai, RisuAI, Inkwell, Chub — читатели V2/V3 читают `data`, старые импортёры читают плоские поля V1 в том же файле |
| Карточка SillyTavern в PNG | `.png` | SillyTavern, Tavo, Chub, RisuAI, Agnai. Единственный контейнер, несущий портрет *и* карточку в одном файле |
| Лорбук / World Info | `.lorebook.json` | SillyTavern, Tavo |
| Чат Character.ai | `.chat.jsonl`, `.chat.json`, `.chat.md`, `.chat.txt`, `.chat.ooba.json` | SillyTavern (JSONL), text-generation-webui (Ooba), любой читатель текста (Markdown и пример диалога) |
| JSON JanitorAI | `.jai.json` | Ближе всего к исходной записи |
| Простой текст | `.txt` | Всё, что читает текст — единственный путь на платформы без импортёра карточек (Character.ai, Crushon, Polybuzz, Emochi) |

Файлы чата предлагаются только на странице чата Character.ai, потому что только там расширение читает историю. **Save chat** скачивает все пять сразу; выбирать формат на странице не нужно.

Если платформа вообще принимает карточку, отправляйте PNG. У JSON-карточки нет поля изображения ни в одной версии спецификации; у PNG есть.

Всё происходит локально. Ничего не загружается, аналитики нет, внешний код не подгружается.

## Как инструмент устроен

Расширение — это четыре небольшие части, у каждой одна задача, и одно правило, которое держит всё вместе: **каждый читатель сайта выдаёт один и тот же объект карточки**.

```
страница сайта
   │
   ├─ src/scraper.js    читает JanitorAI
   ├─ src/emochi.js     читает Emochi (страницы персонажей и Lab)
   ├─ src/polybuzz.js   читает Polybuzz
   ├─ src/cai.js        читает Character.ai + экспортирует чаты
   ├─ src/crushon.js    читает Crushon.ai
   ├─ src/saucepan.js   читает Saucepan.ai
   ├─ src/chub.js       читает Chub.ai + Venus.chub.ai
   ├─ src/wyvern.js     читает WyvernChat
   │       ▲
   │       └─ src/intercept.js + src/harvest.js
   │          (сайты, отдающие запись только своему клиенту)
           │
           ▼
     один объект карточки
     { name, creator, avatarUrl, gender, tags,
       fields: { description, personality, scenario,
                 greeting, altGreetings, exampleDialogue },
       creatorNotes, systemPrompt, postHistoryInstructions,
       extensions, lorebooks[], scriptRefs[] }
           │
           ├─ src/exporters.js  ──▶ .card.json / .png / .lorebook.json / .jai.json / .txt
           └─ src/panel.js      ──▶ интерфейс на странице: список блоков, флажки, экспорт
```

1. **Чтение.** Читатель того сайта, где вы находитесь, собирает персонажа. Каждый делает это по-своему, потому что у каждого сайта своя поверхность: у JanitorAI внутренний JSON API плюс хранилище гидратации на странице, у Emochi бэкенд на Next.js с компилированным промптом, у Polybuzz отрендеренная на сервере полезная нагрузка Nuxt плюс REST API, Chub и Wyvern публикуют записи в форме Tavern через собственные API, а Character.ai и Crushon.ai отдают запись только своей собственной странице — там расширение перехватывает то, что страница уже загрузила, вместо того чтобы спрашивать самому.
2. **Нормализация.** Сырая запись разворачивается в объект карточки. Здесь же переводятся имена полей: `sceneBrief` из Polybuzz становится `description`, `speechText` — `greeting`, `templateIntro` — `scenario`. Ничего не выдумывается. Если поле не опубликовано, оно остаётся пустым.
3. **Показ.** Панель перечисляет найденные блоки с флажком и превью, чтобы можно было убрать попавшую в карточку строку джейлбрейка или системный промпт. Счётчик сверху (`x/y kept`) точно говорит, что будет записано.
4. **Экспорт.** `toBlocks()` превращает отмеченные блоки в нужный формат. Экспортёр не знает сайтов: он никогда не слышал ни про Emochi, ни про Polybuzz, он знает только объект карточки. Поэтому каждый сайт получает все пять форматов бесплатно.
5. **Сохранение.** Создаётся Blob и нажимается через `<a download>`. Сеть не задействована.

В `toBlocks()` есть намеренная защита: если блок Personality оказывается посимвольно равен блоку Description, он молча отбрасывается. Почти всегда это сервер, переливающий одно поле в другое, а не автор, дважды написавший один и тот же абзац.

### Почему расширение, а не сайт

Каждый из этих сайтов держит хотя бы часть данных за авторизованной сессией. Веб-приложению понадобились бы ваши cookie; расширение может одолжить сессию, которая уже есть у браузера, и никогда не видит ваш пароль. В этом вся причина, почему инструмент живёт там, где живёт.

## Установка (около двух минут)

Программировать не нужно. Собирать и компилировать нечего.

1. **Скачайте проект.** Зелёная кнопка **Code** на странице GitHub, затем **Download ZIP**. Распакуйте в постоянное место, например на рабочий стол.
2. **Откройте страницу расширений.** Chrome: `chrome://extensions`. Edge: `edge://extensions`.
3. **Включите режим разработчика** (переключатель справа сверху).
4. Нажмите **Load unpacked** / **Загрузить распакованное** и выберите папку, в которой лежит `manifest.json`.

> Если переместить или удалить эту папку, расширение перестанет работать. Держите её на постоянном месте.

## Использование

### JanitorAI

1. Откройте персонажа на [janitorai.com](https://janitorai.com), будучи авторизованным.
2. Нажмите **Extract card** в правом нижнем углу.
3. **Quick scan** читает персонажа. **Deep scan** дополнительно обходит все привязанные лорбуки — медленнее, полнее.
4. Снимите галочки с ненужного. **Select all** / **Select none** для этого и есть.
5. Выберите формат экспорта.

Если у персонажа больше одного лорбука, после глубокого сканирования появляется кнопка **Separate books** — чтобы общий мир-лорбук сохранился отдельным переиспользуемым файлом.

### Emochi

1. Откройте персонажа на [emochi.com](https://emochi.com) (`emochi.com/character/...`).
2. **Quick scan** читает публичную нагрузку: имя, слоган/описание, приветственное сообщение, теги, аватар, автора.
3. **Deep scan** дополнительно запрашивает определение автора: личность, сценарий, примеры диалогов. Этот маршрут отвечает только для персонажей **вашего аккаунта**; сначала войдите.

У части персонажей Emochi действительно нигде не сохранён текст личности или сценария: сайт ведёт их тегами и генерирует персону в момент чата. Это свойство персонажа, а не сбой чтения.

### Polybuzz

1. Откройте персонажа на [polybuzz.ai](https://polybuzz.ai) (`polybuzz.ai/es/character/chat/...`).
2. **Extract card** → **Quick scan**.
3. Экспорт.

Карточка Polybuzz содержит то, что сайт публикует:

| Поле карточки | Источник в Polybuzz |
|---|---|
| Description | `sceneBrief` — короткое вступление |
| Greeting | `speechText` — начальное сообщение |
| Scenario | `templateIntro`, если бот шаблонный; иначе ремарка, которую автор написал в начале приветствия |
| Personality | теги **Personalidad**, выбранные самим автором (`Frío`, `Celoso`, `Tsundere`…), плюс стиль диалога, если он опубликован |
| Gender | `sceneGender`, как строка `Gender: Male/Female/Non-binary` в описании |
| Теги, аватар, имя, автор | запись сцены |

### Character.ai

1. Откройте персонажа на [character.ai](https://character.ai) с активной сессией (`character.ai/character/...`).
2. Дождитесь загрузки страницы, затем **Extract card** → **Quick scan**.
3. Экспортируйте.

| Поле карточки | Источник в Character.ai |
|---|---|
| Имя, автор, аватар | запись персонажа |
| Description | `title` (слоган), затем `description` (текст «About») |
| Greeting | `greeting` |
| Пример диалога | `definition` — свободный текст определения от автора, если он публичный |

**Об определении.** Character.ai прячет определение персонажа за вторым переключателем автора — **Definition Visibility**, отдельным от видимости персонажа. Когда он выключен, сайт не отправляет текст никому, поэтому блок примера диалога выходит пустым, и панель говорит об этом в сноске. Остальные поля есть независимо от него.

Читатель работает, наблюдая за запросами самой страницы: небольшой скрипт в мире страницы (`src/intercept.js`) копирует заголовок `Authorization` в скрытый тег и переотправляет каждый JSON-ответ как событие DOM, откуда его забирает читатель. Он никогда не изменяет запрос и не отправляет свой с вашим токеном. Когда страница ещё не сделала вызов, читатель спрашивает в таком порядке: контекст самой страницы с захваченным заголовком и её cookies, тот же вызов через service worker с cookies, полученные нагрузки и серверные данные, и, наконец, страница персонажа, загруженная как HTML, с вырезанной из потока записью. Заголовок используется ровно таким, каким его отправила страница: сайт применял и `Token`, и `Bearer`, а пересборка схемы даёт 401.

**С 0.11.2** эта трасса говорит, что вернул каждый этап, вместо `no answer`. Ответ 200 не считается ничем, если не несёт запись персонажа, поэтому строка теперь читается `200, no character in body (status,error)` или `200, html page instead of json` — две формы, которые дают интерстициал Cloudflare и перемещённый эндпоинт. Мёртвый контекст расширения читается `runtime: extension reloaded - reload this tab`, единственная неисправность, не связанная с Character.ai.

#### Save chat (путь экспорта CAI Tools)

Откройте чат (`character.ai/chat/...`), дайте ему загрузиться и нажмите **Save chat**. Кнопка есть только на странице чата. Она скачивает пять файлов:

| Файл | Что это | Куда |
|---|---|---|
| `<имя>.chat.jsonl` | Чат Tavern: сначала строка метаданных, затем `{name, is_user, is_system, is_name, send_date, mes}` на сообщение | SillyTavern → импорт **Chat history** |
| `<имя>.chat.json` | Та же переписка плюс `chat_id`, персонаж, источник и время экспорта | Архив или собственные скрипты |
| `<имя>.chat.md` | Читаемая расшифровка с заголовком на каждого собеседника | Чтение, публикация, печать |
| `<имя>.chat.txt` | `<START>`, затем строки `{{user}}:` / `{{char}}:` | Блок примера диалога карточки |
| `<имя>.chat.ooba.json` | Пары `{internal, visible, data, data_visible}`, начиная с первого хода пользователя | text-generation-webui |

Эндпоинт ходов отдаёт сначала новые и листает через `meta.next_token`. Читатель проходит его до конца, берёт ответ, указанный в `primary_candidate_id` — тот, что реально был на экране, — и сортирует от старых к новым. Если чат длинный, строка состояния считает ходы во время листания.

**Что CAI Tools делает, а это — нет.** CAI Tools также заменяет интерфейс чата Character.ai, управляет фонами, шрифтами, закреплённой памятью, аватарами и системой карточек/библиотеки/поиска, а также рендерит журналы чата в PDF через jsPDF. Это либо функции интерфейса, либо зависимости от встроенных библиотек, поэтому они вне экспортёра, который обязан оставаться без зависимостей. Экспортная половина — поля персонажа, приветствия, аватар и скачивание чата в переносимых форматах — портирована. Markdown печатается в PDF из любого браузера, если PDF действительно нужен.

### Crushon.ai

1. Откройте персонажа на [crushon.ai](https://crushon.ai) (`crushon.ai/character/...`).
2. Дождитесь загрузки страницы, затем **Extract card** → **Quick scan**.
3. Экспортируйте.

Crushon полностью рендерится на клиенте, поэтому читатель берёт запись, которую страница уже отрисовала, вместо вызова API. Псевдонимы полей покрывают все написания, которые сайт использовал между релизами: `firstMessage` / `first_mes` / `greeting`, `description` / `introduction` / `intro`, `avatar` / `avatarUrl` / `image`, `mes_example` / `exampleDialogue` / `dialogue`. Если страница ещё не запросила персонажа, перезагрузите её и просканируйте снова.

**О названиях полей.** Импортёр Crushon отображает карточку Tavern в обратном порядке: `personality` карточки становится *Introduction* в Crushon, а `description` карточки становится *Personality* в Crushon. Читатель записывает то, что публикует Crushon, в то поле карточки, которое означает то же самое, — поэтому проход через оба инструмента оставляет текст там, где он был.

### Saucepan.ai

1. Откройте companion на [saucepan.ai](https://saucepan.ai) (`saucepan.ai/companion/...`), с выполненным входом, если нужны определение и лорбуки.
2. Дождитесь загрузки страницы, затем **Extract card** → **Quick scan**. **Deep scan** добавляет лорбуки.
3. Экспортируйте.

| Поле карточки | Источник в Saucepan.ai |
|---|---|
| Имя, автор, аватар | запись companion |
| Описание | подзаголовок (`short_description`), затем Профиль → **Description** |
| Личность | Core → **Information**, плюс Дополнительно → **Advanced Prompt** и **Formatting Instructions**, если автор их заполнил |
| Приветствие | первая публичная запись Сообщения → **Starting Messages** |
| Альтернативные приветствия | каждое остальное публичное стартовое сообщение |
| Пример диалога | Сообщения → **Example Dialogue** |
| Теги | теги companion и его фандомы |
| Лорбуки | каждый прикреплённый лорбук, одна запись на главу |

**Прокси — это поле, а не ворота.** Saucepan помечает каждый companion политикой провайдеров — *custom and vetted*, *vetted only* или *internal only*, последняя означает отсутствие внешней модели. Эта политика стоит в строке примечания карточки, и больше от неё ничего не зависит; companion экспортируется одинаково, разрешает его автор прокси или нет.

**Почему описание иногда выглядит зашифрованным.** Это не шифрование, это список фрагментов. `GET /api/v2/companions/{id}` отдаёт Description как `{mask, version, fragments: [{key, proof, text}]}`, где большинство фрагментов — приманки со случайным текстом: `"signal glance window but"`, `"simple quiet maybe almost"`. Фрагмент настоящий только тогда, когда его `proof` совпадает с хешем FNV-1a от его собственного текста, с зерном из маски и из `key ^ mask`; выжившие сортируются по `key ^ mask` и склеиваются. `decodeFragments` в `src/saucepan.js` — это та самая процедура, и тесты прогоняют её на фрагментах, скопированных из живого ответа. Без неё вы экспортировали бы наполнитель.

**Публичные companion, с открытым определением или без.** Публичная запись всегда несёт имя, подзаголовок, Description, теги, фандомы, портрет и политику провайдеров, поэтому публичный companion всегда экспортируется как карточка персонажа. Определение — Core, пример диалога, продвинутый промпт, форматирование — это отдельный маршрут и отдельный переключатель автора **Definition Visibility**. Когда он закрыт, Saucepan не отправляет текст никому, карточка выходит с пустыми блоками, а панель называет блоки, которые автор закрыл. Стартовые сообщения тоже отдаются только когда сценарий публичен; когда их нет, блок приветствия пуст и панель это пишет.

**Companion, которые принадлежат вам**, читаются через `GET /api/v1/companion/editable`: он возвращает сырую запись редактора — текст Core, пример диалога, продвинутый промпт, инструкции форматирования и каждый стартовый сценарий независимо от его видимости. Принадлежность проверяется при каждом сканировании, поэтому ваши собственные боты приходят полными даже при закрытом Definition Visibility.

### Chub.ai и Venus.chub.ai

1. Откройте персонажа на [chub.ai](https://chub.ai) или [venus.chub.ai](https://venus.chub.ai) (`/characters/автор/имя`). Для публичной карточки вход не нужен, для всего приватного — нужен.
2. Нажмите **Extract card** → **Quick scan**. **Deep scan** добавляет встроенный лорбук и все лорбуки, привязанные к персонажу.
3. Экспортируйте.

Chub — самый простой сайт из всех, потому что он уже хранит карточки Tavern. Сопоставление почти один к одному:

| Поле карточки | Источник в Chub |
|---|---|
| Имя, автор, аватар, теги | `node.definition.name`, первый сегмент `node.fullPath`, `definition.avatar`, `node.topics` |
| Description | `definition.description` — поле заметок автора |
| Personality | `definition.personality`, плюс `definition.tavern_personality`, когда это не точное эхо |
| Scenario, приветствие, альтернативные приветствия | `definition.scenario`, `definition.first_message`, `definition.alternate_greetings` |
| Пример диалога | `definition.example_dialogs` |
| System prompt, инструкции после истории | `definition.system_prompt`, `definition.post_history_instructions` |
| Лорбуки | `definition.embedded_lorebook`, затем каждый положительный id в `related_lorebooks` |

**Почему используется worker.** `api.chub.ai/api/characters/...` не отправляет `Access-Control-Allow-Origin`, поэтому fetch из контекста страницы отклоняется, хотя API публичный. Service worker расширения не подчиняется CORS и имеет разрешение хоста `api.chub.ai`, поэтому выполняет это чтение. Эндпоинт лорбуков отправляет `*`, так что там работает любой транспорт.

**Дубликаты отбрасываются по содержимому, а не по id.** Персонаж может встроить книгу и одновременно указать её как связанную. Каждая запись сводится к `keys + content`; связанная книга, чья подпись идентична встроенной, пропускается. `-1` — это сентинел в `related_lorebooks`, а не id книги.

**Venus — тот же сайт под другим хостом.** Venus.chub.ai отдаёт ту же SPA, те же пути и тот же API, поэтому один читатель и один набор разрешений покрывают оба. Панель указывает, с какого хоста читала.

### WyvernChat

1. Откройте персонажа на [app.wyvern.chat](https://app.wyvern.chat) (`/profiles/автор/characters/имя`).
2. Нажмите **Extract card** → **Quick scan**. **Deep scan** добавляет все лорбуки, привязанные к персонажу.
3. Экспортируйте.

| Поле карточки | Источник в WyvernChat |
|---|---|
| Имя, автор, аватар, теги | запись персонажа; `creator.vanityUrl`, затем `displayName` |
| Description | `description`, затем `visual_description`, когда он ещё не повторяется |
| Personality, scenario, приветствие | `personality`, `scenario`, `first_mes` |
| Альтернативные приветствия | `alternate_greetings`, плюс продвинутые `greetings`, не являющиеся записью `default` |
| Пример диалога | `mes_example` |
| System prompt | `pre_history_instructions` — редактор называет это **System Prompt** |
| Инструкции после истории | `post_history_instructions` — редактор называет их **Final Instructions** |
| Заметка персонажа | `character_note`, переносится в `extensions.depth_prompt` на глубину 4 |
| Заметки автора | `creator_notes` — **Long Description**; может содержать HTML по замыслу |
| Лорбуки | `GET /api/lorebooks/character/{id}` |

**Пользовательские слаги разрешаются со страницы.** URL Wyvern может использовать внутренний id (`_Ytaz4tYBerdx7zPzp14VD`) или выбранное автором имя (`eveline`). API разрешает только id; запрос имени возвращает 404. Для пользовательского слага читатель разбирает серверный flight-пейлоад Next.js, берёт `id` записи и затем вызывает API. Тот же пейлоад служит запасной записью, когда API отказывает.

**Сопоставление следует собственному экспортёру Wyvern.** В его бандле есть писатель карточек V2. Он сопоставляет `pre_history_instructions` с `system_prompt`, а `character_note` с `extensions.depth_prompt.prompt`; этот читатель делает то же. `creator_notes` экспортируется дословно, даже когда автор заполнил её полной HTML-страницей профиля, потому что именно так поступает собственная загрузка Wyvern.

## Tavo: почему карточка приходила без картинки

Три неисправности, закрыты в 0.11.0 и 0.11.1.

**PNG был корректной карточкой, но только в блоке V2.** PNG-карточка хранит свой JSON в base64-блоках `tEXt`: `chara` для спецификации V2 и `ccv3` для V3. Расширение писало только `chara`. Tavo читает `ccv3`, не находит его и отвечает *«No se detectaron metadatos PNG»* на абсолютно валидный файл. Теперь пишутся оба, в том же порядке и формате, что у SillyTavern, а тесты проверяют оба блока и их CRC через `zlib.crc32`. Блоки стоят между `IHDR` и `IDAT`, где их размещает Chub и где их видит читатель, останавливающийся на первом блоке изображения.

**В JSON нет поля для картинки.** Спецификация V2/V3 — только текст, поэтому Tavo создаёт персонажа с пустым портретом. Теперь расширение встраивает портрет как base64 data URI 512×512 (~40 КБ) в `avatar`, `data.avatar` и `data.extensions.avatar`; если фронтенд читает любое из них, картинка появляется без сетевого запроса. Если байты получить не удалось, туда записывается публичный URL.

**Портрет иногда оставался инициалами, потому что не отвечал worker.** Прежний путь загружал аватар через `<img crossOrigin="anonymous">`; в 0.11.0 его заменили вызовом service worker без запасного пути. CDN Emochi отправляют `Access-Control-Allow-Origin: *`, когда в запросе есть `Origin` (в прошлом замере его не было), так что проблема была не в CORS, а в worker. С 0.11.2 сначала пробуется worker — единственный путь для `cdn.crushon.ai`, который требует cookie сессии, — а при неудаче картинка загружается напрямую. Если не выходит и так, панель называет причину (`the extension was reloaded - reload this tab`, `http 403`, `decode failed`) вместо молчаливой плитки с инициалами.

Chrome один раз отключает расширение после обновления, потому что манифест добавляет разрешения хостов для этих CDN. Включите его снова на странице расширений.

**Какое поле аватара читает Tavo — ответ в 0.12.0.** Документированный объект персонажа Tavo содержит `avatar` (URL или путь к изображению), а `tavo.character.import(card)` принимает либо полную обёртку `{spec:"chara_card_v3",data:{…}}`, либо голый объект `data`. APK 1.9.0 был распакован, и в его `libapp.so` выполнен поиск: там есть `chara_card_v2`, `chara_card_v3`, `ccv3`, `creator_notes`, `mes_example`, `alternate_greetings`, `first_mes`, `character_book` и `extensions.`, но **нет `avatar_url`**. Значит, `data.avatar` — тот JSON-слот, который Tavo может прочитать; `data.extensions.avatar` и верхнеуровневый `avatar` пишутся для других читателей, а не потому, что Tavo они нужны. Последнее слово всё равно за диалогом импорта: если ваша сборка Tavo игнорирует там data URI, импортируйте PNG, где картинка — это сам файл.

### Если читатель всё ещё говорит «нет метаданных PNG»

Панель теперь говорит, что построила. В подвале — запущенная версия, а строка состояния после экспорта PNG перечисляет текстовые блоки файла:

```
PNG сохранён - chara + ccv3 - 486 КБ - v0.12.0.
```

Если в этой строке обе клавиши, файл правильный, а читатель смотрит в другое место. Если их нет, не удался сам экспорт. Размер нужен, чтобы сравнить файл на диске с только что построенным; `- плитка инициалов` означает, что портрет получить не удалось и была нарисована градиентная плитка.

Файл из отчёта, породившего этот раздел, был проверен побайтно: один блок `tEXt`, ключ `chara`, перед `IDAT`, валидный CRC и ни одного ключа `avatar` в JSON. Это подпись 0.10.0. Экспортёр 0.11.x всегда пишет два блока и поле `avatar`. Поэтому прежде всего:

1. **Проверьте, что в подвале `v0.12.0`.** Если там `v0.10.x` или `v0.11.x`, браузер запускает старую сборку.
2. **Включите расширение заново и перезагрузите вкладку.** Chrome один раз отключает распакованное расширение при изменении разрешений, а уже открытая вкладка держит старый content script до перезагрузки. Экспорт из такой вкладки даёт старый файл с новым именем — именно так выглядит отчёт «всё ещё не работает».
3. **Экспортируйте снова.** Файлы на диске сохраняют старые байты. Скачайте PNG ещё раз после перезагрузки.

Чтобы проверить файл напрямую: его первый текстовый блок должен декодироваться в объект JSON с `"spec": "chara_card_v2"`, второй — в `"chara_card_v3"`, и `data.avatar` должен существовать.

### Портрет часто был плиткой инициалов, а не персонажем

Портрет — единственная часть экспорта, зависящая от service worker расширения, поэтому именно она отказывает, когда worker недоступен. Измеренные с заголовком `Origin` и без него, хосты портретов ведут себя так:

| Сайт | Хост портрета | `Access-Control-Allow-Origin` |
|---|---|---|
| Emochi | `image-cdn.flowgpt.com`, `cdn.mokio.ai` | `*`, когда запрос несёт `Origin` |
| Polybuzz | `cdn.polyspeak.ai` | `*` |
| Character.ai | `characterai.io` | `*` |
| JanitorAI | `ella.janitorai.com` | `*` |
| Crushon.ai | `cdn.crushon.ai` | отсутствует; 403 без cookie сессии |
| Saucepan.ai | `saucepan.ai/cdn/<id>/card` | не нужен, тот же origin |

Заметка 0.11.0 в этом файле утверждала, что хосты Emochi не отправляют заголовок CORS. Тот зонд не посылал `Origin`, а эти CDN отражают полученный заголовок. С браузером впереди `image-cdn.flowgpt.com` и `cdn.mokio.ai` отвечают `Access-Control-Allow-Origin: *`, и загрузка `<img crossOrigin="anonymous">` работает — проверено в настоящем Chromium, а не чтением заголовков.

Значит, плитка инициалов никогда не была проблемой CORS. Проблемой был worker: `chrome.runtime.sendMessage` ничего не возвращает, когда расширение перезагрузили при открытой вкладке, когда разрешение хоста не выдано или когда service worker завершился по таймауту. Экспортёр называл это ошибкой и рисовал плитку, не имея способа узнать, какой из трёх случаев произошёл.

0.11.2 меняет три вещи:

- **Второй транспорт.** Сначала пробуется worker (единственный путь для `cdn.crushon.ai`, которому нужен cookie сессии), затем портрет загружается как cross-origin изображение. Emochi, Polybuzz, Character.ai и JanitorAI теперь получают картинку даже с мёртвым worker.
- **Без постоянной защёлки.** Карточка, у которой не получился портрет, повторяется при следующем экспорте, а не запоминает ошибку на всю жизнь вкладки.
- **Причина на экране.** Строка состояния заканчивается `- плитка инициалов (<причина>)`: `the extension was reloaded - reload this tab`, `http 403`, `decode failed: …` или `the record has no portrait URL`. Мёртвый контекст расширения называется таковым, а не выглядит сломанным CDN.

Поскольку манифест называет эти хосты портретов, Chrome один раз отключает расширение после обновления, пока вы не включите его снова на странице расширений.

## Polybuzz: информацию о предыстории получить нельзя. Вот почему.

Руководство по созданию в Polybuzz перечисляет семь составляющих персонажа: имя, пол, короткое вступление, приветствие, теги, **предысторию** и **стиль диалога** (плюс пример диалога, задающий стиль). Публичная страница отдаёт пять. Остальные две — `systemRole` (предыстория, обозначена как *Antecedentes*) и `conversationExample` (примеры диалогов) — **не отправляются никому, кроме автора этого персонажа**. Это не недостающий эндпоинт и не то, что можно обойти этим или любым другим расширением, потому что **данные собираются на сервере и никогда не сериализуются для не-владельца**.

Доказательства, кратко:

- Сама форма создания показывает поле как `Antecedentes (Visto en privado)` — *Antecedentes, видно только приватно*. Это заметка только для автора, по замыслу.
- Все маршруты API только для чтения, которые знает веб-клиент, были вызваны к публичным ботам со свежей гостевой сессией. Единственный, где вообще есть этот ключ, — `scene/detailguest`, и он возвращает `""`.
- Маршрут владельца `scene/getscenedetail` отвечает `210002` на бота, которым ваш аккаунт не владеет. Этот код окончателен: сервер отказывает в записи.
- Во всех 225 лениво загружаемых JavaScript-чанках сайта `systemRole` и `conversationExample` встречаются в **одном** файле — на странице создания. Ни одна другая страница их не запрашивает, значит, ни одна не может их показать.
- Контрольный эксперимент закрывает вопрос: бот, у которого в Antecedentes стоит метка `ZZZ-123`, просканированный со второго аккаунта, метку не показал ни разу. Значение не покидает сессию автора.
- Попросить модель процитировать собственные инструкции тоже не работает. Конвейер чата собирает системный промпт на сервере, а поток несёт только текстовые фрагменты. Когда у бота спросили его биографию, он уверенно выдумал детство, которого не было. Пересказ — не сохранённый текст, и это расширение не выдаёт генерацию за извлечение.

**Что расширение делает вместо этого:** использует поля, которые Polybuzz действительно публикует, и говорит об этом в сноске под списком блоков. Personality берётся из тегов, выбранных автором; Scenario — из начальной ремарки приветствия, дословно. Ничего не пересказывается и не выдумывается.

Если персонаж ваш, все три авторизованных маршрута по-прежнему опрашиваются при каждом сканировании, и ваши боты возвращаются полностью.

## Как этот форк создавался, от начала до конца

Короткая запись: форма процесса объясняет, почему ограничения выше заслуживают доверия.

1. **Начать с исходного инструмента.** Апстрим-расширение уже читало JanitorAI. Оно стало базой, и правило для всего дальнейшего было: никогда не менять унаследованное поведение, только добавлять рядом.
2. **Добавить читатель, а не особый случай.** Emochi добавлен как `src/emochi.js`, заполняющий тот же объект карточки, поэтому `exporters.js` и `panel.js` не потребовали изменений вообще.
3. **Найти настоящую нагрузку.** Emochi — приложение Next.js на бэкенде FlowGPT; полезные данные лежат в скомпилированной строке `initPrompt` внутри публичного объекта промпта. Эта строка разбирается обратно на личность, предысторию, сценарий и пример диалога.
4. **Измерять, а не предполагать.** Утверждение, что Emochi публикует определение примерно для трети персонажей, получено на трёх независимых живых выборках (30, 19 и 9 персонажей) с подсчётом. Это флаг публикации (`visibility: true`), а не входной барьер.
5. **Добавить Polybuzz так же.** Nuxt рендерит персонажа на сервере прямо в страницу, поэтому нагрузка лежит в DOM как массив devalue. Этот массив разворачивается и обыскивается. Content script не видит `window.__NUXT__`, поэтому используется тег `<script id="__NUXT_DATA__">`.
6. **Перечислить API, а не угадывать его.** JavaScript-бандл сайта объявляет 214 конфигураций запросов. Все доступные только для чтения были вызваны к публичным ботам. Так и получен вывод «предыстория недостижима» — не одним провалом, а исчерпанием поверхности.
7. **Доказать отрицание контролем.** Эксперимент с `ZZZ-123` на двух аккаунтах превратил «мы не находим» в «этого там нет, чтобы найти».
8. **Держать панель молчащей.** Отсутствующее приватное поле автора — норма, а не ошибка. Панель показывает сноску, а не баннер. Сообщение получает только настоящий сбой (не выполнен вход, ни один маршрут не ответил).
9. **Тестировать всё, что тестируется.** `node --test` покрывает читатели, нормализатор, экспортёры и сборщик блоков. 137 тестов на момент написания. Каждое утверждение об API в этом README проверено на живом сайте, а непроверяемые помечены как таковые.
10. **Записать.** Раздел для разработчиков существует, чтобы следующему человеку не пришлось выводить всё заново.
11. **Сначала переиспользовать, потом писать.** Character.ai и Crushon.ai отдают запись только своему JavaScript, поэтому один механизм покрывает оба: сниффер в мире страницы и проход с оценкой по нагрузкам. По одному новому файлу на сайт, два общих — и экспортёры не тронуты.
12. **Указывать источник подхода.** Схема перехвата взята из [экспортёра taquanta](https://github.com/taquanta/character-ai-to-crushon-ai-card-exporter), и упоминание стоит в начале файла и в этом README, а не только в сообщении коммита.
13. **Говорить, что не проверено.** Оба новых сайта отвечают `403` от Cloudflare машине без браузера, поэтому контракты задокументированы, а живое чтение — нет. Это написано в трёх местах вместо того, чтобы быть обойдённым.
14. **Читать собственный экспортёр сайта, когда он есть.** Wyvern несёт в бандле писатель карточек V2. Его извлечение решило `pre_history_instructions` → `system_prompt`, `character_note` → `extensions.depth_prompt` и `creator_notes` как Long Description. Сопоставление, скопированное из кода продукта, лучше выведенного из интерфейса.
15. **Не считать API всей записью.** JanitorAI пишет того же персонажа в страницу как `window.mbxM.push(JSON.parse("…"))` — строку JSON внутри документа JSON. API говорил, что определения нет; страница несла запись. Разбор скрипта гидратации и был разницей между сводкой и карточкой.
16. **Портировать функции, а не код.** CAI Tools определило практические форматы чатов; читатель пишет их своим кодом, сохраняет правило без зависимостей и говорит, какие функции CAI Tools являются интерфейсом и потому вне области.

**Инструмент активно развивается и будет получать обновления.** Добавляются сайты, чинятся сломанные читатели, заметки по API правятся, когда сайт меняется. Если что-то сломалось, обычно это значит, что сайт изменил форму нагрузки, — и это исправимо.

### 0.12.0 — три сайта, хранилище гидратации и экспортная половина CAI Tools

**Chub был первым сайтом, которому не понадобился переводчик.** Его API персонажей возвращает объект `definition`, ключи которого уже являются ключами Tavern: `description`, `personality`, `scenario`, `first_message`, `alternate_greetings`, `example_dialogs`, `system_prompt`, `post_history_instructions`, `tavern_personality`, `embedded_lorebook`. Worker уже существовал для Emochi и Polybuzz, поэтому чтение переехало туда под разрешение хоста `api.chub.ai`. Лорбуки были вторым вопросом: `related_lorebooks` несёт id, `-1` — сентинел, и книга может быть одновременно встроенной и связанной. Свести каждую книгу к подписи `keys + content` и отбросить точные повторы оказалось достаточно; ни одному списку id не доверяли.

**Wyvern выглядел проблемой пользовательского слага, а оказался проблемой пейлоада.** `/api/characters/{id}` чист, но URL сайта используют выбранный автором слаг, а `eveline` — не id. API отвечает 404 на имя. Однако страница рендерит всю запись в flight-пейлоад Next.js. Разбор блоков `self.__next_f.push` и вырезание записи сопоставлением скобок даёт и id, и запасной вариант. Затем бандл ответил на вопрос о сопоставлении лучше любых догадок: Wyvern включает собственный писатель V2, и он говорит `system_prompt: e.pre_history_instructions`, `post_history_instructions: e.post_history_instructions`, `creator_notes: e.creator_notes` и `depth_prompt.prompt: e.character_note`. Чтение поймало две ошибки 0.12.0: первый читатель терял System Prompt из 935 символов, потому что смотрел на `system_prompt`, и обращался с объектами продвинутых `greetings` как со строками. Обе исправлены, и тесты используют имена полей самого сайта.

**Определение JanitorAI не отсутствовало; оно было экранировано.** API по-прежнему отвечает `personality: null` и `showdefinition: true` анонимному вызову, что выглядит противоречием, пока не заглянешь в страницу. Приложение Vite гидратирует свои хранилища через `window.mbxM.push(JSON.parse("{\"SJ--a:a-a--characterStore\":{…}}"))` — строковый литерал JSON, содержащий документ JSON. Старый читатель искал уже декодированный `{"id":…}` и ничего не находил. `scriptPayloads()` теперь разбирает литерал, затем результат, и проход с оценкой находит объект персонажа внутри хранилища. Тот же пейлоад понесёт определение для авторизованного читателя, потому что это копия, которую сервер отрендерил для этой сессии. Анонимная запись остаётся сводкой, и панель теперь говорит это точно: автор пометил определение как публичное, но эта сессия его не получила. Это другое сообщение, чем «автор его скрыл», и разница важна в отчёте об ошибке.

**CAI Tools разобрали, а не скопировали.** Его экспортёр чатов определяет пять форматов: читаемый, Tavern JSONL, JSON Oobabooga, текст определения и PDF. Первые четыре соответствуют правилу без зависимостей. Файлу Tavern нужна строка метаданных и `is_name`; файлу Oobabooga — объединение пар и старт с первого хода пользователя. Теперь создаются оба, вместе с JSON-архивом, Markdown и примером диалога. PDF исключён намеренно: он использует jsPDF и аватары, а достоверный Unicode PDF без встроенного шрифта здесь невозможен. Markdown печатается в PDF из браузера. Остальное в CAI Tools — замена страницы чата, фоны, шрифты, закреплённая память, библиотека, поиск — не экспортёр и не воспроизводится.

**PNG проверяли в браузере, а не только в Node.** Живую запись JanitorAI прочитали, дали ей запись лорбука, нарисовали на плитке 512×512 с настоящим портретом и записали как PNG. Затем файл прочитали обратно: `IHDR, tEXt (chara), tEXt (ccv3), IDAT…`; оба base64-блока декодировались в валидный JSON V2/V3 с записью книги; транспорт портрета сообщил `cors`, а не плитку инициалов. Это сквозное доказательство, которого не дают юнит-тесты: canvas, `btoa`, `TextEncoder`, CRC и размещение блоков в том же браузере, который будет запускать расширение.

**Что всё ещё не проверено.** Авторизованные чтения JanitorAI, Character.ai и Crushon.ai остаются недоступными: хосты отвечают 403 Cloudflare машине, на которой всё это собиралось, а встроенный браузер не имеет сессии аккаунта. Контракты документированы; авторизованное чтение — нет. Chub, API Venus, id- и пользовательские слаги Wyvern, анонимное чтение JanitorAI и восстановление из хранилища гидратации проверялись на живых сайтах.

### 0.11.2 — портрет, который существовал только в панели

**Две карточки экспортировались серыми буквами, и файл говорил почему.** Два PNG Alana Flores несли `chara` + `ccv3` в правильном месте, а `data.avatar` содержал верный URL `image-cdn.flowgpt.com`. Карточка была в порядке, а картинка никогда не загружалась: `prepareAvatar()` отработал, `requestImage()` вернул пустоту, и нарисовалась плитка инициалов. Панель продолжала показывать фото, потому что превью — обычный `<img>`, которому не нужна механика расширения.

**Объяснение 0.11.0 было неверным, и повторное измерение показало почему.** Та версия утверждала, что `image-cdn.flowgpt.com` и `cdn.mokio.ai` не отправляют `Access-Control-Allow-Origin`. Зонд, на котором это основывалось, не посылал `Origin`. Пошлите его — как делает каждый браузер — и оба хоста ответят `Access-Control-Allow-Origin: *`. CDN никогда не был проблемой; worker был. Загрузка `<img crossOrigin="anonymous">` работает, и 0.11.0 заменила именно её вызовом worker без запасного пути. Затем обе ветви проверили в настоящем Chromium: сначала `avatarSource=worker`, data URI на 99 КБ и PNG-карточка на 526 КБ; затем из манифеста убрали `https://*.flowgpt.com/*`, чтобы worker не достал CDN, и получили `avatarSource=cors` с теми же байтами и тем же портретом.

**Что изменилось.** Worker остаётся первым транспортом, потому что `cdn.crushon.ai` отвечает 403 без cookie сессии, а его несёт только worker. Загрузка CORS — запасной путь. Постоянная защёлка `avatarReady` исчезла, поэтому карточка, неудавшаяся однажды, повторяется при следующем экспорте. И строка состояния называет отказ: `- плитка инициалов (worker unreachable: the extension was reloaded - reload this tab)` или `- плитка инициалов (http 403)` вместо вида проектного решения. Ошибка Character.ai в том же отчёте была той же нехваткой информации: её трасса заканчивалась `no answer` на каждом шаге worker, что и выглядит как потерянный контекст расширения из content script. Теперь она сообщает ошибку runtime, а 200 без ничего пригодного говорит, какую форму получила.

### 0.11.0 — карточка была валидной, читатель хотел другой блок

**Два отчёта, один формат файла.** PNG, отклонённый Tavo с *«No se detectaron metadatos PNG»*, и импорт JSON, который загрузил персонажа, но оставил портрет пустым. Оба воспроизвели на файле, который расширение реально пишет, а не на сайте.

**PNG был валидной карточкой V2.** Порядок блоков, поля длины и CRC32 проверили против `zlib.crc32` побайтно: сигнатура, `IHDR`, блок `tEXt` под ключом `chara` с base64 JSON, затем нетронутые данные изображения. Ничего не было искажено. Не хватало второго блока. SillyTavern пишет `chara` и `ccv3`; Tavo ищет `ccv3` первым и сообщает об отсутствии метаданных вместо использования другого. Один блок был всей разницей между отклонённым и принятым файлом. Теперь пишутся оба, в этом порядке, и тест утверждает полный список `IHDR, tEXt, tEXt, IDAT, IEND` с каждым CRC, проверенным zlib.

**В JSON никогда не было слота для картинки.** Спецификация V2/V3 — только текст. Импорт JSON в Tavo всегда создаёт персонажа с пустым выбором портрета, что и показывал скриншот. Единственный способ поместить изображение в JSON — data URI, поэтому экспорт теперь встраивает JPEG 512×512 (~40 КБ) в `avatar`, `data.avatar` и `data.extensions.avatar`. Если фронтенд читает любой из них, картинка приходит без сетевого запроса. Tavo документирован как берущий изображение из PNG или из выбора, поэтому честный ответ для этого приложения: PNG для картинки и карточки вместе, JSON для текста.

**Аватар падал до начала.** Старый код загружал портрет с `crossOrigin = "anonymous"`, что требует `Access-Control-Allow-Origin` в ответе изображения. Зондирование пяти CDN ответило прямо: `image-cdn.flowgpt.com` и `cdn.mokio.ai` без заголовка, `cdn.polyspeak.ai`, `characterai.io` и `ella.janitorai.com` с `*`, `cdn.crushon.ai` с 403 без cookie. Для Emochi загрузка CORS не получала даже байта, поэтому экспорт молча падал на плитку инициалов и выглядел сработавшим. Теперь портрет идёт через `background.js` с разрешением хоста на каждый CDN, возвращается в base64 и декодируется через `createImageBitmap`, которому не нужен CORS и который не может испортить canvas. Неудачный fetch всё ещё падает на плитку, но теперь ошибка означает неудачный fetch, а не неверный режим. Это стоит пяти новых разрешений хостов, поэтому Chrome один раз отключает расширение при обновлении, пока его не включат снова.

### 0.10.0 — Saucepan и описание, которое приходит кусками

**Сайт не таков, каким кажется снаружи.** `api.saucepan.ai` сбрасывает соединение для всего, что не браузер, что обычно означает Cloudflare и тупик. Тупика не было: базовый URL приложения — пустая строка, поэтому каждый вызов идёт на `https://saucepan.ai/api/...` и проксируется на краю. Тот же origin, без CORS, и статический заголовок, который клиент ставит на каждый запрос (`cf-edge-token-8af3`). Это открытие сделало весь сайт читаемым без браузера.

**Затем контракт полей, из бандла, а не из догадки.** Приложение несёт бандл на 9,8 МБ со всем API. Он объявляет 666 путей запросов. Схема валидации редактора companion называет каждое поле, которое хранит сайт — `card`, `full_description`, `short_description`, `example_dialogue`, `starting_scenarios[]`, `advanced_prompt`, `formatting_instructions`, `hidden_fields`, `external_model_policy` — а компонент профиля называет каждое поле, которое рендерит. Две формы, один продукт; разница между ними — история этой версии.

**Описание — это набор осколков с приманками.** Первый живой публичный companion вернул пятьдесят четыре фрагмента Description, семь настоящих. Приманки — грамматический шум из небольшого словаря — *signal*, *glance*, *window*, *pattern*, *gentle*, *quiet* — поэтому на первый взгляд читаются как проза и переживают наивную эвристику «взять самые длинные строки». Различение — в клиенте: каждый фрагмент несёт `proof`, и он настоящий только когда этот proof равен хешу FNV-1a текста самого фрагмента с зерном из маски и из `key ^ mask`. Настоящие сортируются по `key ^ mask` и склеиваются. Семь фрагментов собрали 137 символов чистого текста. Процедура — `decodeFragments`, проверенная на фрагментах из живого ответа. Стартовые сообщения используют ту же структуру в `starting_scenarios_fragments[].message`; приватный сценарий просто отсутствует, а пустой слот хранится как сентинел `≠≠≠BLANK_SCENARIO≠≠≠`, который читатель отбрасывает.

**Прокси были вопросом, и ответ — `providers_profile`.** Поле называется `external_model_policy` в редакторе и `providers_profile` в публичной записи: `custom_and_vetted`, `vetted_only`, `internal_only`. Оно определяет, какую модель может вызвать чат, а не что отдаёт профиль, поэтому сообщается в строке примечания и больше ни для чего не используется. Обе политики экспортируются одинаково. Есть два пути чтения, потому что у публичного companion два переключателя видимости: публичная запись анонимна и всегда несёт Description; определение — второй вызов, требует bearer из `localStorage["hallucination/auth_token"]` и отклоняется, когда автор закрыл Definition Visibility. У вашего companion есть третий путь, `/api/v1/companion/editable`, который возвращает сырую запись редактора и не заботится о видимости. **Что не проверено:** маршруты определения и editable требуют сессии, поэтому их формы взяты из клиентского кода, который их потребляет, а не из авторизованного вызова; публичный маршрут, декодер фрагментов, политика провайдеров и фрагменты сценариев проверялись на живых companion. 103 теста, 11 новых.

### 0.9.0 — два закрытых сайта, один механизм и парсер Emochi с тремя ошибками

**Сначала Emochi, потому что это был приоритет.** Открытыми были два сообщения: отсутствие личности и сценария у части ботов и `characterExampleConversation`, который так и не доходил до карточки.

Ошибка с примерами диалогов заняла десять минут. Маршрут определения возвращает `characterExampleConversation` как **массив ходов**, а читатель применял к нему `String(...)`. Массив превращается в `"[object Object],[object Object]"` в одних средах и в `""` в хелпере `s()` нормализатора — в любом случае это не диалог. Теперь он разбирается как ходы, и парсер принимает `{role, content}`, `{user, ai}`, `{isUser, text}` и обёртку `{dialogue: [...]}`, потому что собственный рекордер Emochi использует первую форму, импортёры карточек — вторую, а остальные встречаются в записях до смены схемы.

Ошибка с личностью заняла больше времени и оказалась тремя наложенными дефектами:

1. **Закрывающая инструкция считалась границей.** Каждый скомпилированный промпт заканчивается строкой `Do not write as {{user}} or assume {{user}}'s reaction or response.` Читатель обрезал текст там и выбрасывал весь хвост. Это правильно для промпта, который заканчивается правилом, — то есть для того, что создаёт компилятор. Это неправильно в тот момент, когда автор цитирует правило внутри своей предыстории или своего примера диалога, а случается это чаще, чем кажется: люди намеренно вставляют правило в свой пример, чтобы научить модель. Каждая секция после цитаты исчезала. Исправление — убирать это предложение там, где оно встречается, и сохранять текст вокруг.
2. **Грамматика секций принимала ровно одно написание.** Маркерами были `'s personality:`, `'s background:`, `scenario of role-play:`. Автор, написавший `Personality:` — с заглавной, без притяжательного, потому что писал свой промпт вместо конструктора, — получал пустой разбор, и весь промпт уходил в ветку «маркеров нет, считай это личностью». Теперь есть второй набор маркеров, привязанный к началу строки и терпящий отклонения, и побеждает проход, распознавший больше секций. При равенстве остаётся строгая грамматика, поэтому промпты компилятора разбираются точно как раньше.
3. **Примечание о пустых секциях было догадкой.** Читатель сообщал «автор оставил личность и пример диалога пустыми» всякий раз, когда эти поля выходили пустыми — включая случаи, когда парсер вообще не распознал разметку, и поля были пустыми из-за парсера. Теперь примечание срабатывает только когда распознана и строка имени, то есть разметка действительно понята.

Все три покрыты тестами, написанными из падающих форм, а не из проходящих.

**Затем примеры диалогов Polybuzz.** В тикете был скриншот редактора *Estilo de diálogo*: строки с аватаром рядом — это `{{user}}`, строки без — `{{char}}`. Чтение бандла страницы создания подтвердило форму: `dialogueStyleObj` — массив пар `{user, ai}`, по одной на обмен, а запись деталей возвращает его под `dialogueStyle.dialogue`. Оба теперь разбираются в строки карточки. Плоская строка `conversationExample` — те же данные как `user;ai` на строку, и эта форма тоже переписывается.

Одна ловушка: простая строка под `dialogueStyle` — это **метка стиля** (`Descriptivo, frases cortas`), а не диалог. Первая версия парсера бодро переписала метку стиля в `{{char}}: Descriptivo, frases cortas` и положила её в блок примеров. Тесты поймали. Теперь строки никогда не становятся диалогом; только массивы и текст `user;ai`.

**Затем Character.ai.** Подход взят из [экспортёра taquanta](https://github.com/taquanta/character-ai-to-crushon-ai-card-exporter), который решил ту же задачу: запись запрашивает только JavaScript самой страницы, с заголовком `Authorization: Token <hex>`, который расширение не может выписать. Референсная реализация запускает скрипт в мире страницы (`MAIN`), перехватывает `fetch` и `XMLHttpRequest` и сохраняет заголовок в DOM. Это единственный способ увидеть заголовок, который браузер добавляет вне вашего контекста.

Два изменения. Токен попадает в мета-тег с собственным пространством имён вместо того, который может столкнуться. И каждый JSON-ответ, который получает страница, переотправляется как событие DOM, несущее **строку**, — объекты не пересекают границу между скриптом `MAIN` и изолированным content script, а строки пересекают. Это единственное изменение превратило сниффер из «поймай токен и повтори вызов» в «поймай токен *и* ответ», поэтому читатель продолжает работать, когда повтор отклонён.

Определение — интересное поле. Character.ai прячет его за **Definition Visibility**, вторым переключателем, отдельным от видимости персонажа, и когда он выключен, текст не отправляется никому. Поэтому карточка с пустым блоком примера диалога — это настройка автора, а не неудачное чтение, и панель говорит именно это вместо показа ошибки.

**Затем Crushon.ai.** Полностью рендерится на клиенте, за стеной защиты от ботов. Публичного API для повтора нет, а вызовы страницы несут состояние сессии, поэтому читатель ничего не вызывает: он проходит по нагрузкам, которые страница уже получила, и оценивает каждый объект по числу известных имён полей. Побеждает самый богатый. Псевдонимы покрывают написания, которые сайт использовал между релизами, потому что пропущенное написание стоит целого поля.

Общая часть обоих читателей — `src/harvest.js`: сбор нагрузок, перечитывание токена и проход с оценкой. Два новых читателя, два общих файла, ноль изменений в `exporters.js` или `panel.js` — правило, что каждый читатель заполняет один и тот же объект карточки, сделало это возможным, и оно же означает, что следующий сайт стоит одного файла.

**Что не удалось проверить.** Оба новых хоста отвечают `403` от Cloudflare машине, на которой это собиралось, поэтому ни один из читателей не проверялся против браузера с сессией. Что проверено: эндпоинт neo жив и отвечает `{"status":"NOT_OK","error":"bad request"}` на синтетический идентификатор — то есть маршрут ругается на тело, а не на вызывающего. Контракты полей взяты из работающей реализации taquanta. Это записано как непроверенное в changelog, в планах и здесь, потому что не запускавшийся читатель — это другое утверждение, чем запускавшийся.

### 0.8.0 — у форка появляется имя и шесть языков

Репозиторий всё ещё носил исходное имя, поддерживая четыре сайта. Переименован в **Universal Character Card Exporter** — это то, что он делает. Issues включён тогда же, потому что раздел о сообщениях об ошибках отправлял людей во вкладку, которой не существовало.

Документация переведена на шесть языков за один проход. Справочник по API для каждого сайта остаётся на английском и говорит об этом в начале раздела: это справочный материал, который устаревает быстрее всего, а шесть копий устаревшего документа — это шестикратное обслуживание без выгоды. Переводы ссылаются туда.

Раздел Polybuzz переписан. Раньше там был вывод «получить нельзя». Теперь под ним лежат доказательства — метка приватности по замыслу в форме создания, исчерпывающий обход маршрутов, `210002` на чужом боте, контрольный тест `ZZZ-123` на двух аккаунтах. Утверждённый отрицательный результат не стоит ничего; отрицательный результат с приложенным методом стоит чего-то.

### 0.7.13 — личность из тегов самого автора

Polybuzz не публикует ни предысторию, ни поле личности, из-за чего блок Personality в карточках оставался пустым. Дерево тегов уже запрашивалось для списка тегов карточки, поэтому его прочитали внимательнее: каждый тег лежит под одним из четырёх родителей, а `Personalidad` содержит 41 слово темперамента, которые автор выбирает вручную. Это характеристика автора, написанная им, опубликованная сайтом.

Соединение честно в конкретном смысле: теги жанра, происхождения и идентичности остаются вне Personality и в списке тегов, а настоящий `systemRole` по-прежнему важнее тегов, когда он есть. Измерено на 10 живых ботах: 10/10 дали настоящий блок Personality. Список тегов тоньше написанной предыстории, но это слова автора, а не догадка.

### 0.7.10 – 0.7.12 — эхо это не поле

Три релиза, одна идея. `getsceneconfig` с идентификатором сцены отвечает скомпилированным текстом вступления как запасным вариантом. Пять авторизованных сканирований ботов, которыми аккаунт не владеет, вернули `systemRole`, посимвольно совпадающий с `sceneBrief`. Так сервер рендерит пустую предысторию, а не второе поле, которое случайно совпало. Точное эхо теперь считается отсутствием, каждый маршрут сохраняет свой ответ вместо первого непустого, а панель показывает сноску вместо баннера, потому что приватное поле автора — это норма.

Сценарий вышел из той же работы: приветствия Polybuzz часто начинаются с ремарки (`*Bangchan es tu esposo*`), а это предпосылка самого автора. Она переносится дословно, когда в записи нет `templateIntro`. Пересказа не бывает никогда.

## Это разрешено?

Это инструмент личного резервного копирования. Он читает то, что вы и так видите авторизованным, и сохраняет это в открытом формате. Он не обходит платные стены и не открывает ничего, чего вы не могли бы увидеть.

Условия сайтов могут всё же ограничивать автоматический доступ. Используйте для своих персонажей и личных копий, указывайте авторов при повторной публикации их работы и не нагружайте сайты.

## Приватность

- Данные отсканированных персонажей никогда не покидают браузер. Без аналитики, без внешнего кода.
- Разрешения хостов ограничены сайтами из манифеста, их API-хостами и их CDN портретов; разрешения `<all_urls>` нет.
- Единственные сетевые вызовы — к сайту, на котором вы уже находитесь, к API этого сайта и к его хосту портретов.

## Для разработчиков

Расширение — чистый JavaScript без зависимостей и без сборки. Правьте `src/` и перезагружайте со страницы расширений.

```sh
node --test
```

`src/scraper.js` читает JanitorAI, `src/emochi.js` — Emochi, `src/polybuzz.js` — Polybuzz, `src/cai.js` — Character.ai, `src/crushon.js` — Crushon.ai, `src/saucepan.js` — Saucepan.ai, `src/chub.js` — Chub.ai/Venus.chub.ai, `src/wyvern.js` — WyvernChat. Все восемь заполняют одну форму карточки, поэтому экспортёры и панель никогда не знают, на каком вы сайте. `src/exporters.js` преобразует, `src/panel.js` и `src/panel.css` — панель на странице, `background.js` — service worker для запросов, которые content script сделать не может (CORS, запрещённые заголовки).

Два файла существуют только для сайтов, которые никогда не публикуют запись через API: `src/intercept.js` работает в мире самой страницы (`world: "MAIN"`, `document_start`) и копирует в DOM то, что страница уже знает; `src/harvest.js` собирает эти нагрузки и оценивает каждый объект против списка известных имён полей. Третий закрытый сайт стоит одного файла, где объявлены его ключи.

**Запись API по сайтам находится в английском README** ([Developer reference](README.md#developer-reference-english-only)). Она намеренно остаётся на английском: это справочный материал и часть, которая быстрее всего устаревает при изменениях на сайте. Переводы ссылаются на неё.
